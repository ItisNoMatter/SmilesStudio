# 0066: TDDワークフローを5ステップ・各ステップ確認必須の形式に再定義する

- Date: 2026-09-04
- Status: Accepted
- Category: process
- Deciders: the user

## Context

CLAUDE.mdのTDDワークフローは、これまでTest First/Red/Green/Refactorの4ステップで、一度に
テスト作成から実装まで進める運用だった。ユーザーから、コンパイルエラーによる「構造のRED」と、
テスト実行による「振る舞いのRED」を明確に分離し、各ステップの完了ごとに状況報告と確認を挟む、
より厳格な5ステップのプロセスへ再定義したいという明示的な指示があった。

## Decision

CLAUDE.mdの「開発ワークフロー（TDDサイクルの徹底）」を以下の5ステップに再定義する。各ステップの
完了後、次のステップに進む前に必ず状況を報告し確認を待つ（一気に実装まで進めない）。

1. テストコードの作成（この時点ではコンパイルエラーになる想定＝構造のRED）
2. コンパイルエラーの解消（スケルトン実装。空のクラス・メソッド、ダミー値や`TODO()`で通す。
   まだ振る舞いは実装しない）
3. 振る舞いのRED確認（テストを実行し、期待値と異なる／例外で失敗することを確認し出力を提示）
4. 実装（GREEN、最小限のロジックでテストを通す）
5. リファクタリング（可読性の見直し、Kotlinらしい書き方に整理）

## Alternatives

本文中に明示的な代替案の比較記述はなし。ユーザーが直接の方針として指定し、そのまま反映した
（複数アプローチを比較検討するような設計フォークではなく、具体的な手順そのものが指示された
ため）。

## Consequences

- 今後のTDD実装は、これまでのようにテスト作成→実装をまとめて進めるのではなく、5ステップの
  それぞれで一度立ち止まりユーザーの確認を待つ運用になる。1機能の実装完了までのやり取りの
  往復回数が増える。
- 「構造のRED」（コンパイルエラー）と「振る舞いのRED」（テスト失敗）を別ステップとして明示的に
  分離したことで、テスト対象のシグネチャ（引数・戻り値の型）を先に固定してから振る舞いを
  実装する、という順序がより徹底される。
- `./gradlew allTests`によるグリーン確認・失敗時の自律的な原因分析と修正という既存の運用ルールは
  変更なく維持する。
